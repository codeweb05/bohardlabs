# lib

The showcase for every UI package in this repo.

Stories live next to the source they document, inside `packages/*/src/`. This app only
aggregates them, so a story imports its component the same way a consumer's editor would.

## Stories are the tests

Every story here runs as a real test in a real Chromium, through
`@storybook/addon-vitest`:

- a `play` function is an interaction test. Run them with
  `pnpm --filter @bohardlabs/storybook test`.
- the a11y addon is set to `test: 'error'`, so an axe violation fails the run rather than
  quietly colouring a panel.

One story file is the demo, the interaction test, and the accessibility check. A story with
no `play` asserts nothing and will drift from the component it claims to document.

Each story also narrows its own controls to the props it is demonstrating. `DataTable` takes
77 of them, and a panel that lists all 77 on every story says nothing about which ones that
story is about. The complete list is on the component's docs page.

## What the table does not do

Two things people look for and do not find, on purpose:

- **No import.** There is an export menu (CSV, and Excel and JSON when you widen
  `exportFormats`), but nothing reads a file in. Parsing, column mapping, validation and the
  write belong to the app's data layer, not to a component that renders what it is handed.
- **No i18n runtime and no data fetching.** The table takes translated strings through
  `labels` and takes rows through `data`. Both are the app's, and the guides show the wiring.

## Themes

The toolbar's theme picker repaints every story under a different `createTheme` call. Eight
are set up:

| Theme            | The design, not just the palette                                                 |
| ---------------- | -------------------------------------------------------------------------------- |
| Light, Dark      | stock MUI, no app tokens at all                                                  |
| Nord             | arctic and flat: soft radius, hairline rules, nothing floats on a shadow         |
| Dracula          | loud: pill controls, 2px outlines, uppercase buttons, a glow under every overlay |
| Tokyo Night      | a terminal: square corners, monospace throughout, hard rules, no shadow anywhere |
| Solarized Light  | printed matter: warm paper, serif headers, dashed hairlines, near-square corners |
| Catppuccin Latte | a design system: no row rules at all, 14px radius, everything on a soft shadow   |
| High contrast    | the accessibility end: square, 2px outlines, 3px header rule, uppercase and bold |

The stock two carry no app tokens on purpose: a component that only looks right under one
product's palette is not ready to publish, and that shows up first against a bare baseline.

The other six change shape, not only hue. Colour alone makes six themes that differ in one
axis and prove very little; radius, rule weight, outline weight, whether a menu floats or
sits inside a border, and whether a button shouts in uppercase are the properties most likely
to be wrong in a component that was only ever built against one app. Each of the six is a
plain `createTheme` call and nothing else. The package's source does not change, the stories
do not change, and no colour, radius or font is hardcoded anywhere in it.

What a theme reaches, and what it does not, is in
**[Guides → Theming](?path=/docs/guides-theming--docs)**. The short version: palette, divider,
hover, radius, font and the header's treatment are the theme's; row height, cell padding, body
font size and header case are the `density` and `headerCase` props.

## Every story carries its own code

Under each story in the canvas is a **Show code** / **Copy** bar, holding the same JSX the
docs page shows: the component call with the args currently set in the Controls panel, not
the story object and not its `play` function. Change a control and the snippet follows.

It stays collapsed until asked for. An open code block under every story would double the
height of the canvas, and its text would sit inside the same root the `play` functions and
the axe pass read, where it can only add noise.

Two things that usually resist theming are props instead. `slots.confirmDialog` replaces the
bulk-action confirmation with the app's own dialog, so a project with an existing one does
not end up with two that look different, and `dateFormats` sets what the date filter shows
and what it sends.

## Viewports

The device list in the toolbar resizes the preview. It matters for `DataTable`, which drops
its table markup for a card list below `mobileBreakpoint`; the **MobileCards** story pins
itself to a phone.
